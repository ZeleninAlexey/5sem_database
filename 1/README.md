## Предметная область

Организация хранит товары на складах, разделённых на ячейки, получает их
от поставщиков и отгружает получателям.
Поступление и отгрузка представлены общей сущностью «документ» с типом `IN`
или `OUT`; отдельные позиции хранятся в строках документа.
Каждая строка определяет товар, ячейку, количество и цену единицы:
закупочную для поступления и отпускную для отгрузки.
Остаток равен сумме поступлений минус сумма отгрузок по товару и ячейке.

Границы учебной модели:

- Все документы считаются проведёнными, черновики и статусы не учитываются.
- Документ может включать ячейки разных складов; склад определяется через ячейку.
- В ячейке может находиться несколько товаров, а товар может храниться в нескольких ячейках.
- Партии, сроки годности, сотрудники и перемещения между складами не моделируются.
- Получатель — название в документе, отдельный справочник клиентов отсутствует.
- Пороги `min_stock` и `max_stock` — справочные значения по организации;
  они не ограничивают фактический остаток.
- Дробные количества разрешены для всех единиц измерения.
- Запрет отгрузки сверх остатка не реализован: он требует проверки нескольких строк
  с учётом конкурентных операций; представление позволяет обнаружить отрицательный итог.
- Документ может существовать без строк; наличие хотя бы одной строки не проверяется.

## Сущности и связи

| Таблица | Назначение | Основные данные |
| --- | --- | --- |
| `warehouses` | Склады | Идентификатор, уникальный код, название, адрес |
| `storage_cells` | Ячейки | Идентификатор, склад, код внутри склада |
| `products` | Товары | Идентификатор, артикул, название, единица, пороги запаса |
| `suppliers` | Поставщики | Идентификатор, название, ИНН, необязательный телефон |
| `documents` | Поступления и отгрузки | Идентификатор, тип, номер, дата, поставщик или получатель |
| `document_lines` | Позиции документов | Документ, номер строки, товар, ячейка, количество, цена |

Все связи — «один ко многим»: склад → ячейки, поставщик → документы поступления,
документ → строки, товар → строки и ячейка → строки.
У строки ровно один документ, товар и ячейка; у ячейки ровно один склад.
Ссылка документа на поставщика обязательна только для `IN`.

## Основные проектные решения

1. Поступления и отгрузки объединены в `documents` и `document_lines`:
   у них общая структура и различающийся тип операции.
2. `document_type` принимает только `IN` или `OUT`.
   `CHECK` реквизитов требует поставщика и отсутствие получателя у `IN`,
   а у `OUT` — непустого получателя и отсутствие поставщика.
   Поэтому `supplier_id` и `recipient_name` допускают `NULL` на уровне столбцов,
   но обязательность нужного реквизита обеспечивается CHECK.
3. Ограничения объявлены без явных имён: PostgreSQL назначает их автоматически.
   Самостоятельные сущности имеют `bigint GENERATED ALWAYS AS IDENTITY`;
   бизнес-коды защищены отдельными UNIQUE.
4. Ключ строки — `(document_id, line_no)`;
   номер строки может повторяться в разных документах.
5. `UNIQUE (warehouse_id, code)` разрешает `A-01` на разных складах;
   `UNIQUE (document_type, document_no)` разрешает одинаковый номер для разных типов документов.
6. Количество хранится в `numeric(12, 3)`, цена — в `numeric(12, 2)`;
   точные значения подходят для дробных количеств и денежных сумм.
   Даты имеют тип `date`, ИНН и коды — строковые типы.
7. `ON DELETE RESTRICT` защищает используемые склады, ячейки, товары и поставщиков.
   `ON DELETE CASCADE` удаляет строки вместе с документом;
   это меняет расчётный остаток, что разрешено учебной моделью.
   Для изменения ключей действует стандартное `ON UPDATE NO ACTION`.
8. Остаток вычисляется в `stock_balances` через `CASE` и `SUM`:
   `IN` добавляет количество, `OUT` вычитает.
   Комбинации товара и ячейки без движений в представлении отсутствуют.

## Обоснование 3НФ

**1НФ:** поля содержат одиночные значения, позиции документа вынесены в отдельные строки.

**2НФ:** поля `document_lines` зависят от всей пары «документ + номер строки»;
у остальных таблиц первичный ключ одиночный.

**3НФ:** при принятых правилах неключевые атрибуты не определяют другие
неключевые атрибуты в той же таблице.

| Таблица | Функциональная зависимость |
| --- | --- |
| `warehouses` | `warehouse_id → code, name, address`; код — альтернативный ключ |
| `storage_cells` | `cell_id → warehouse_id, code`; пара «склад + код» — альтернативный ключ |
| `products` | `product_id → sku, name, unit, min_stock, max_stock`; артикул — альтернативный ключ |
| `suppliers` | `supplier_id → name, tax_id, phone`; ИНН — альтернативный ключ |
| `documents` | `document_id → document_type, document_no, document_on, supplier_id, recipient_name`; пара «тип + номер» — альтернативный ключ |
| `document_lines` | `(document_id, line_no) → product_id, cell_id, quantity, unit_price` |

Название товара находится только в `products`, сведения о поставщике — в `suppliers`,
склад ячейки — в `storage_cells`, а тип и дата документа — в `documents`.
В строках эти сведения не дублируются.
Цена зависит от конкретной позиции документа, а название получателя фиксируется
в конкретном документе без других реквизитов клиента.
Тип документа задаёт допустимость NULL в реквизитах, но не определяет конкретного
поставщика или конкретное имя получателя для всех документов.

## Файлы и порядок выполнения

1. `schema.sql` — создание шести таблиц, ограничений и представления.
2. `data.sql` — однократное заполнение связными данными.
3. `constraints_test.sql` — 12 отклоняемых INSERT/UPDATE и проверки RESTRICT/CASCADE.
4. `migration.sql` — комментарии до получения дополнительного требования.

Скрипты рассчитаны на отдельную пустую базу PostgreSQL:

```powershell
createdb -U postgres warehouse_lab1
psql -U postgres -d warehouse_lab1 -v ON_ERROR_STOP=1 -f schema.sql
psql -U postgres -d warehouse_lab1 -v ON_ERROR_STOP=1 -f data.sql
psql -U postgres -d warehouse_lab1 -v ON_ERROR_STOP=1 -f constraints_test.sql
```

При необходимости замените `postgres` своей учётной записью.
Эта версия файлов описывает новую исходную модель;
она не преобразует уже созданную БД с прежней структурой.
Если та уже существует, новую версию можно запустить в другой пустой базе.

В тестах временная функция `pg_temp.expect_rejection` перехватывает нарушение,
сравнивает SQLSTATE, затем выводит `NOTICE: OK`.
Неожиданный успех или другая ошибка прерывает тест.
Последний `ROLLBACK` восстанавливает удалённый для проверки CASCADE документ.
Пропуски в последовательностях ID после неудачных INSERT допустимы.

## Просмотр остатков

```sql
SELECT w.code AS warehouse, c.code AS cell, p.sku,
       p.name, b.quantity, p.unit
FROM stock_balances AS b
JOIN products AS p USING (product_id)
JOIN storage_cells AS c USING (cell_id)
JOIN warehouses AS w USING (warehouse_id)
ORDER BY w.code, c.code, p.sku;
```

Ожидаемый результат по количествам:

| Склад | Ячейка | Артикул | Остаток |
| --- | --- | --- | ---: |
| MSK | A-01 | BOLT-M8 | 480.000 |
| MSK | A-01 | NUT-M8 | 380.000 |
| MSK | A-02 | CABLE-3 | 110.250 |
| MSK | B-01 | PAINT-W | 65.000 |
| TVER | A-01 | BOLT-M8 | 150.000 |
| TVER | B-01 | SAND-Q | 950.000 |

Для подготовленных данных запрос ниже должен вернуть пустой результат:

```sql
SELECT * FROM stock_balances WHERE quantity < 0;
```
